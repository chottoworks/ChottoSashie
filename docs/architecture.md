# アーキテクチャ設計書

## 1. 全体構成

```text
Tauri 2 (Windows)
  └─ React / TypeScript UI
       └─ 127.0.0.1 FastAPI
            ├─ SQLite（業務データ・ジョブ・履歴）
            ├─ ジョブ実行（応答返却後の常駐処理）
            ├─ 診断／モデル管理
            └─ ComfyUI APIクライアント
```

Tauriはウィンドウ、プロセス起動、OSダイアログ、配布を担当する。Reactは利用者向けワークフローだけを表示する。FastAPIが唯一の業務APIとなり、ファイル、DB、ComfyUIへのアクセスを集約する。重い計算はすべてComfyUIが受け持つ（人物ごとの学習をやめたので、アプリが起動する生成用の子プロセスは無い）。

## 2. プロセス境界

- `desktop`: UI起動時にアプリ専用Python環境のAPIをループバック限定で起動し、終了時に子プロセスを停止する。
- `api`: 入力検証、DBトランザクション、診断、セットアップ、ジョブ操作を提供する。重い処理はHTTP応答を返した後の常駐処理として実行し、要求の応答時間には含めない。
- `comfyui`: 管理モードでは固定バージョンの専用環境、外部モードでは利用者指定URLを使用する。専用環境の本体は共有フォルダに置き、アプリが準備・更新する。

APIの番号は8766番から順に空きを探す。1つに決め打ちすると、たまたま同じ番号を使う別のプログラムがあるだけで、利用者はそれを探し出して止めるまでこのアプリを使えない。開いているだけでは繋がず、`/health` で正体（`app`）と保存先まで確かめてから相乗りするか避けるかを決める。決めた番号は起動時にWebViewへ渡す（画面が決め打ちの番号へ繋ぎに行って空振りしないため）。

起動したAPIは、Windowsのジョブオブジェクト（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）へ入れる。後片付けはウィンドウの破棄で行っているが、タスクマネージャー等で強制終了されたときには走らない。そのままではAPIのPythonが残り、ポートと保存先を掴み続ける。ジョブへの参照はこのプロセスが持ち続け、消えるときにOSが閉じる——閉じた時点で中の処理が終わるので、どんな終わり方でも取りこぼさない。子がさらに起動したもの（専用ComfyUI）も同じジョブに入るため、まとめて終わる。**すでに動いているAPIへ相乗りした場合は入れない**——自分が起動していないものを道連れにしない。

読み取り（GET）はトークンで守らない。ブラウザの `<img>` がヘッダを付けられず、画像がすべて表示できなくなるためである。そのぶん、応答を読める送信元を絞る——デスクトップ版が起動したAPI（トークンを渡されている側）では、開発用の `localhost:1421` を許さない。配布した先でその口を開けたままにすると、たまたま1421番を使う別のプログラムから作品や画像を読み出せてしまう。

生成用Pythonは巨大で競合しやすいため、API用Pythonから分離する。APIは安定した軽量依存だけを持ち、生成ランタイム（ComfyUI）の破損時にも診断と修復UIを起動できるようにする。この分離はプロセス境界で担保し、API自身は計算を行わない。

配布版では、APIを動かすPythonもアプリに同梱する。開発時はリポジトリの `.venv` を使うが、配布先にはリポジトリも仮想環境も無い。ビルド時のパス（`CARGO_MANIFEST_DIR`）を実行ファイルへ焼き込んで `.venv` を探す作りでは、ビルドした本人の環境でしか動かない。同梱するのは公式のWindows埋め込み可能パッケージで、`installer/build_api_runtime.py` が版を固定して取得し、依存とアプリ本体を入れた一式を作る。ビルド時のパスに頼るのはデバッグビルドだけとし、配布する実行ファイルには残さない。PyInstallerのような単一実行ファイル化を採らないのは、中身が普通のファイルのままなら利用者の環境で起きた不具合をそのまま追えること、ウイルス対策ソフトの誤検知を招きにくいこと、そして専用ComfyUI同梱の埋め込み版Pythonをすでに同じ考え方で扱っていることによる。

同梱物は、site-packagesの奥ではなくその外（`app`）へ置き、起動時に `CHOTTO_SASHIE_RESOURCES_DIR` で場所を教える。site-packagesの下に置くと `chotto_sashie_shared/_resources/` のぶんだけ深くなり、導入先の長い環境でWindowsの260文字制限に当たる。

アプリに付いてくる読み取り専用のファイル（ワークフロー、マニフェスト）は、**どこから読むかを1箇所で決める**（`shared_env.app_resources_root`）。リポジトリ内で動かす開発時、`pip install` で入れた状態、配布版では場所が違う。リポジトリからの相対位置に決め打ちすると、リポジトリの外へ出した時点で何も見つからなくなる。探す順は「環境変数 `CHOTTO_SASHIE_RESOURCES_DIR` → パッケージの隣の `_resources` → 親をたどって両方のフォルダが揃っている場所」とし、どれにも当たらなければ止める。近そうな場所を返すと、起動はするのに生成だけが失敗するという原因の見えない壊れ方になるためである。同梱物はWindowsの260文字制限を食うので、深さには上限を設けて試験で見張る。

ジョブの実行主体はAPIプロセスとする。単一利用者・単一GPUのデスクトップアプリでは、常駐ワーカーを別プロセスへ分けても得られる利点が少なく、起動順序、ログ、クラッシュ検知、配布が複雑になるためである。この判断の代償として次の二つを明示的に実装する。

- GPUを占有するジョブは `gpu_slots` で常に一件へ直列化する。実行中判定はSQLiteのジョブ状態を根拠とするため、API再起動をまたいでも矛盾しない。
- 起動した子プロセス（専用ComfyUI）は `child_processes` が所有物として追跡し、API終了時に停止する。追跡しないと、DB上は中断なのに実体が動き続ける。

APIを終了しても生成を継続したい要件が生じた場合は、ジョブ実行を独立したワーカープロセスへ移す。その際は上記の直列化判定をワーカー側の取得条件へ移設する。

保存先と共有フォルダは、**インストール先の隣の `paths.json`** に持つ。保存先そのものへ置くと、保存先を変えた瞬間に設定が読めなくなる。実行ファイルの隣なら、インストールを分けたときにそれぞれが別の場所を持てる。決め方は「環境変数 → `paths.json` → 既定」の順で、環境変数を最優先にするのは開発と試験がそれで保存先を隔離しているためである（そこを設定ファイルで上書きすると、試験が実データへ書き込む）。決めた値はAPIの子へ環境変数で渡す——子に決め直させると、設定ファイルを読む側と読まない側で食い違う。

保存先を変える処理は、**APIを止めた状態で単発の子プロセスとして**動かす（`chotto_sashie_shared.data_location`）。APIは自分のDBを掴んだままなので、掴んだ本人が自分の足元を移すことはできない。フォルダを移すだけでは足りず、DBに残る絶対パスも書き換える——書き換えないと「記録はあるのに開けない」状態になる。同じドライブなら付け替え、別ドライブなら複製して数と大きさが一致したことを確かめてから元を消す（途中で失敗したときに何も残らなくならないため）。終わったらアプリごと再起動する。APIだけ入れ替えると、画面が古い保存先の内容を掴んだまま新しいAPIと話すことになる。

複製は元の量だけ時間がかかるため、子プロセスは途中経過を**1行1件のJSON**で流し、最後の1行を結果とする。デスクトップ版は行を読みながら `data-dir-progress` として画面へ渡す（そのためだけに `core:event:default` を許可している）。終わるまで待ってからまとめて読むと、数十GBの複製の間、画面に出せるものが何も無く、止まったのか進んでいるのか区別が付かない。複製そのものも `shutil.copytree` ではなく1ファイルずつ・読み書きを分けて行う——終わるまで何も返さない仕組みでは、大きな1ファイルの途中で進捗が止まって見える。

共有フォルダは数十GBあるため、変えても**中身は移さない**。新しい場所に一式があればそれを使い、無ければ取得し直す。その判断は押す前に伝えて利用者に委ねる。

開発環境と配布版は、**実行するコードは別だが、保存先と共有フォルダは既定が同じ**になる。配布版は自分の同梱Pythonと同梱物だけを使い、リポジトリの `.venv` やソースは見ない（`development_runtime()` はデバッグビルド限定）。一方、保存先（`%LOCALAPPDATA%\ChottoSashie`）と共有フォルダ（`%LOCALAPPDATA%\ChottoSashieShared`）は既定が同じで、インストール先を変えただけでは分かれない。分けたいときは、画面から置き場所を変えるか、環境変数を与える。

さらに、保存先が同じなら配布版は開発中のAPIへ**相乗りする**（同じ番号で二重に起動しないため）。このとき配布版は開発中のコードで動く。開発しながら配布版の動作を確かめたい場合は、保存先を分けるか、開発用APIを止めてから起動する。

## 3. 保存領域

作品の保存先（既定は `%LOCALAPPDATA%\ChottoSashie`、画面から変更可）には、DB（`database`）と、記録ごとの画像・動画を置く。置き場所は `storage.py` などで1か所に決めている。

| フォルダ | 中身 | 持ち主の記録 |
|---|---|---|
| `assets/background_assets`・`assets/prop_assets` | 背景・小物の画像 | 背景・小物 |
| `assets/character-figures` | 立ち絵 | 立ち絵 |
| `assets/character-portraits` | 一覧に出す代表写真 | 人物 |
| `outputs/candidates` | 人物候補の控え | 人物候補 |
| `keyframes` | 合成した静止画 | 静止画 |
| `videos`・`shot-last-frames`・`shot-frames`・`shot-segments` | カットの動画・最終フレーム・構図変更の起点/終端・区間動画 | カット・ビート |
| `exports` | 全カットを1本につないだ動画 | 作品 |
| `managed` | 専用ComfyUIの設定・入出力・ログ | （アプリ） |

**画像・動画は記録の持ち物で、記録を消せば一緒に消す。** 差し替えたとき（作り直し・代表写真を既定へ戻す・1本で作り直して分割の区間が要らなくなった、など）も、使わなくなった方をその場で消す。生成の途中で記録が消された場合は、出来上がったファイルを結び付けられないので、その場で消す（`_record_or_discard`）。それでも、記録を消してからファイルを消すまでの間に落ちた、ファイルが掴まれていて消せなかった、という残り方はありうる。そこで**起動のたびに、どの記録からも辿れないファイルを上の表のフォルダから消す**（`orphans.remove_unreferenced_files`）。記録の中の場所ではなくファイル名で突き合わせるので、保存先を移したあとでも取り違えない。利用者が「名前を付けて保存」で外へ出したものは保存先の外にあるので、どれも消さない。

**アンインストールで「アプリデータも削除」を選んだときは、保存先も片付ける。** インストーラ（Tauri の NSIS）が標準で消すのは識別子の名前のフォルダ（`%LOCALAPPDATA%\jp.chottoworks.sashie` など）だけで、作品の保存先は知らない。そこで、ファイルを消す前の追加処理（`windows/hooks.nsh` の `NSIS_HOOK_PREUNINSTALL`）から `chotto-sashie.exe --remove-user-data` を呼ぶ。保存先は画面を開くときと同じ決め方（環境変数 → `paths.json` → 既定）で実行ファイルが決め、同梱のPythonで `chotto_sashie_shared.data_removal` を動かす。消すのは保存先の直下でこのアプリが作るもの（`APP_ENTRIES`。書き込む側の場所と試験で突き合わせる）だけで、DBが無いフォルダは指し間違いを疑って何もしない。ほかのファイルが残っていればフォルダは残す。置き場所の設定（`paths.json`）も消す——アンインストーラは自分が入れたファイルしか消さないので、残すと入れ直したときに消したはずの保存先が初期値として出てくる。「アプリデータも削除」を選ばなかったときは、残した作品の場所を覚えておくために設定も残す。共有フォルダ（ComfyUI本体とモデル）は、別のインストールや開発環境と共用することがあり数十GBを取り直すことになるため消さない。

ComfyUI本体とアプリが取得したモデルは、アプリのデータ領域とは別の共有フォルダ `%LOCALAPPDATA%\ChottoSashieShared`（`comfyui` と `models`、環境変数 `CHOTTO_SASHIE_SHARED_DIR` で変更可）へ置く。数十GBあるため、保存先の引っ越しに巻き込まないためである。

既存のモデルフォルダは `setup_config.external_model_roots` に読み取り専用の参照として持つ。管理ComfyUI側に生成する `extra_model_paths.yaml` だけが外部ソースを参照し、外部側の設定は変更しない。パス解決後も、管理対象ルートと外部ルートを厳密に区別する。

**ComfyUI側に残る生成物の写しは、専用ComfyUIのときだけ片付ける**（`comfy_scratch`）。ComfyUIは生成物をまず自分の出力フォルダへ保存し、アプリはそれを取り出して保存先へ写す。合成などで送り込んだ画像も入力フォルダに残る。どちらもアプリ側に実体があるので、放っておくと没にした画像まで溜まり続け、作品を消しても消えない。専用ComfyUIの入力・出力フォルダは管理領域（`managed/runtime/comfy/input`・`output`）にあるアプリの持ち物なので、取り出し終えた出力と、生成を見届けたあとの入力をその場で消す。アプリやComfyUIが途中で落ちて片付けまで届かなかった分は、専用ComfyUIを起動する直前（使っている生成が無い時点）に中身ごと消す。既存ComfyUIをそのまま使う場合、そのフォルダは利用者のものなので消さず、書き込まれること自体をそのComfyUIを使う仕様として受け入れる。そのため、生成の起点にComfyUIの出力フォルダを指すことはしない——人物候補は出来た時点で保存先へ控え、立ち絵の起点もその控えから送る（出力フォルダを指すと、片付けた時点で基準画像があるのに立ち絵が作れなくなる）。

不足モデルの取得先は利用者が選ぶ。既定は共有フォルダで、既存モデルフォルダを選んだ場合だけ、そのフォルダへ不足分を書き足す（`setup_config.model_download_root`）。書き込み先は保存時と取得時の両方で「設定済みの参照フォルダであること」「実在して書き込めること」を確かめ、種別のフォルダ名は既存の並び（`unet` / `clip` など）に合わせる。同名で内容が違うファイルがある場合は上書きせず失敗させる。取得済みかどうかは、共有フォルダ・取得先を順に見て判断するため、置き場所を変えても取り直しは起きない。

## 4. SQLite

表は `schema_meta`、`jobs`、`projects`、`characters`、`character_candidates`、`character_figures`、`background_assets`、`prop_assets`、`still_images`、`still_image_characters`、`shots`、`shot_beats`、`shot_speech_lines`、`character_figure_edits`、`prompt_translations`、`setup_config`、`preferences`。初回リリースの形をそのまま定義に書いており、旧版からの移行処理は持たない。

`projects.illustration_style` は作品全体で共通する挿絵画風を保存し、`characters.art_style` は互換性を保ったまま人物固有の小さな雰囲気補正として扱う。`character_figures` は人物の実体である立ち絵を保存する。画像の持ち主はこの記録で、静止画は `still_image_characters.figure_id` から参照するだけにする（静止画を消しても立ち絵は残り、立ち絵を消しても合成済みの静止画は残る）。既定の立ち絵は印を保存せず、読むときに決める——出来上がる順で選択が入れ替わらないようにするためで、保存する印は利用者が選んだ1枚だけを表す。人物の髪型・髪色、目の特徴・目の色は独立した構造化列とし、変えてはいけない特徴は順序を保つJSON配列で保存する。候補画像は人物、親ジョブ、表示順、seed、プロンプト、ComfyUI prompt ID、出力情報、基準選択を永続化する。自動生成seedはバッチごとに暗号学的乱数で更新し、画面とJSONで1刻みを失わないJavaScript安全整数範囲に限定する。候補を作り直すときの前の回は、既定で上書き（基準画像だけ残して消す）とし、設定（`preferences.candidate_history`）で「履歴として残す」に切り替えられる。基準画像を決めたあとは、選ばなかった候補を画像ごとまとめて消せる。人物を削除すると候補と立ち絵も連動して消える。

`still_images` は人物・背景・小物の組み合わせと、合成した1枚を持つ。挿絵としてはこれが完成品で、動画を作る場合は同じ1枚がシーンの起点になる。`shots`（カット）は静止画へ直接ぶら下がり、前カットの最終フレームを次カットの起点へ引き継いで連続性を作る。

カットの起点は「構図変更で作った1枚（`custom_start_frame_path`）→ 前カットの最終フレーム → 元の静止画」の順に決まる。`start_frame_image_path` は「何を起点に使ったか」の記録で、実体は他の記録のもの（前カットの最終フレーム、元の静止画）を指す。**削除では消さない**——カットを1つ消しただけで前のカットの最終フレームが失われ、連続性が壊れる。解決は `readiness.resolve_shot_start_frame` の1か所だけで行い、判定・表示・生成が同じ答えを見る。**実体が無い記録は数えない**（道だけ残ってファイルが消えていることがある）。どれが使われるかは `ShotRead.start_frame_source` として画面へ返し、`GET /api/v1/shots/{id}/start-frame` が実際に使う1枚を返す。画面はその実物をサムネイルで出す——「前カットの続きから始まらない」を目で確かめられるようにするため（黙って静止画へ戻る、という形にしない）。最終フレームはワークフロー側で `ImageFromBatch` + `SaveImage` として保存し、ComfyUIから取得する。動画ファイルからの抽出（webpはPillow、mp4はffmpeg）は取得できなかったときの保険で、これによりffmpegの無い環境でも音声付き（mp4）のカットが連続する。

`shot_beats` はカットの中の時間区間で、長さ・動きの指示・セリフを持つ（開始時刻は先行ビートの長さの合計から導く）。

セリフ・ナレーションは `shot_speech_lines` に**行で持ち、行ごとに話す人**（その静止画にいる人物か、ナレーション）を持つ。持ち主はカット全体（`beat_id` が NULL、ビートが無いときに使う）かビート。誰のセリフでも `the character says` として送ると、二人いる場面でどちらが話すかがモデル任せになる。話す人は見た目と配置で名指しする——静止画の配置（`still_image_characters.spec.placement`）と人物の性別・年齢帯・髪から記述を作り、名指しの句（"the young woman on the left"）へ訳す。名前は使わない（日本語の名前はセリフと区別されず読み上げられる）。手がかりが無くても静止画に1人しかいなければ `the only person on screen` と名指しする。話す人はその静止画の人物に限り、人物を消すと話す人だけ外れて行は残る（`ON DELETE SET NULL`。画面で選び直してもらう）。MiniMax H3 の土台は先頭と末尾以外のキーフレームを受け付けないため、時間の割り振りは2通りで実現する。`timeline_mode = single` はビートを1本のプロンプトへ直列化して1回で生成する（安いが、従うかはモデル次第）。`split` はビートごとに生成し、前区間の最終フレームを次の起点にして繋ぐ（確実だがビートの数だけ時間がかかる）。分割した区間はffmpegがあればカット動画へ連結し、無ければ区間のまま残して書き出しのときに繋ぐ。

**ffmpegはアプリが用意できる**（`ffmpeg_provision`）。書き出し（結合）は `libx264` でH.264へ再符号化するため、x264を含むGPL構成のWindowsビルドを版とタグで固定し、`model-manifests/ffmpeg.json` に記録する。取得はモデルと同じ道（sha256検証・再開付きの `download_with_resume`）を通り、共有フォルダの `tools/ffmpeg/bin/` へ実行ファイルと利用条件だけを置く（再生用の `ffplay` と文書は取り出さない）。書庫の中の道はそのまま使わず、末尾の形（`.../bin/ffmpeg.exe`）で判断して置き先はこちらで組み立てる——版名のフォルダが版で変わるうえ、外へ抜ける細工を効かせないため。同梱も再配布もせず、別プロセスとして呼ぶだけにとどめる。

**つなぐ機能は任意扱いにする。**ffmpegが無くても、カット動画は作ったままの形で取り出せる（下記）。作業が閉じ込められないので、これだけでセットアップの完了を止めない（`optional: true`）。**取得するものがffmpegであることは隠さない**——外部の配布物を入れるので、名前・取得元・利用条件・量を押す前に画面へ出す。

**入口は初期設定の「ComfyUI環境を用意」の最後の手順「ノードとモデルの確認」に置く。**足りないものは1か所にまとめて出したいので、書き出し画面に専用のボタンは作らない（そちらは行き先を示すだけ）。要件マニフェストの機能に `tools` を書けると、ComfyUIのノード・モデルと並べて「この端末に要る道具」を扱える。道具の調べ方は道具ごとに違うため、共通の土台（`requirements.py`）はマニフェストから「何が要るか」だけを読み、「あるか」の判定は呼び出し側から関数で受け取る——土台が個々の道具を知らずに済むように。判定関数を渡さないときは揃っていないものとして扱う（黙って通さない）。動画を作らない設定では、この機能ごと report から外れる。

検出は「設定で指定された場所 → アプリが取得したもの → PATH → よくある導入先（winget・scoop・chocolatey・`C:\ffmpeg`・Program Files）」の順。PATHを通さない導入方法が多く、PATHだけを見ると「入れてあるのに見つからない」が起きる。アプリが取得したものをPATHより先に見るのは、検証済みで `libx264` が確実に入っているため。場所を明示的に指定しているときは用意を勧めない（その指定を直すのが先で、黙って別のものを使わない）。

MiniMax H3 へ渡すプロンプトの組み立て（`shot_video.build_shot_prompt`）は、欄に分けた形にする。

```
integrated_multimodal_description:
[Shot 1]
Single continuous shot, no cuts. Choreography for one unbroken 5-second arc:
Second 0–5: {映像}
（セリフがあれば At 0s the young woman on the left says "…" / 続く行は Then … says "…" /
  ナレーションは an off-screen narrator says "…" と画面の人物に口を合わせさせない指定 /
  無ければ人物を黙らせる指定）

overall_soundscape:
{環境音。無くセリフもあるなら N/A}

non_diegetic_music:
{劇伴。無ければ N/A}
```

**使わない欄は空にせず `N/A` と書く。**要らないと言い切ったほうが効く。声を入れないカットには、唇を閉じたまま・リップシンクの動きなし・発話の種類を数え上げる、という長い無音指定を置く（`SILENCE_DIRECTIVE`）。`No dialogue.` だけでは、書いていないセリフを喋る（実機で繰り返し確認）。**`Audio:` のような行に短い否定を書くと、その文字自体が読み上げられることがある。**

区間は `Second A–B:` の行に割り、**区間が1つでも、ビートを足していないカットでも、尺が分かっていれば常にこの時間付きの形にする**（1区間だけの指定で素直に動いた実機の結果に合わせる）。映像の行にセリフを混ぜない。

**言語の制約と自動変換**: 公式テンプレートのプロンプトは全編英語で、CJK文字は1つも無い。動きの指示とセリフの両方が日本語だと、モデルは両者を区別できず、日本語の断片を尺に入るだけ順に読み上げる（実機で2度確認）。そこで**セリフ以外の指示だけを英語へ直してから送る**（`translation.py`）。翻訳には ComfyUI 標準の `TextGenerate`（`clip.generate()`）を使い、生成できるテキストエンコーダ（既定は `gemma4_e4b_it_fp8_scaled.safetensors`）を `CLIPLoader` で読む。同じ接続先・同じ順番待ちの中で完結し、外部サービスは使わない。出力は `PreviewAny` から履歴経由で受け取る（ファイルを書かないので既存ComfyUIの出力フォルダを汚さない）。結果は `prompt_translations` に覚えておき、同じ文を訳し直さない。翻訳用モデルが無い環境では日本語のまま送り、生成そのものは止めない（要件では `prompt_translation` を `optional` として扱う）。翻訳用モデルは、MiniMax H3 と同じ任意の組（`group: minimax_h3`）でアプリが取得する（H3を使うときだけ要るため）。セリフは訳さない——読み上げてほしい言葉そのものなので、日本語のまま引用符の中へ入れる。セリフの話す人の記述は、指示とは別の訳し方（名指しの句にする）で訳し、覚えるときの鍵も分ける。名指しが訳せなかったときは日本語の記述を文へ入れず、誰とも決めない書き方（`one of the characters`）にする。

**生成に使う文は2段階で作る。** 組み立て（翻訳を含む）と動画生成を分け、組み立て結果を `shots.resolved_prompt_json` へ保存する。動画生成は保存済みの文を送るだけで、無いか古いときだけその場で組み立てる。画面には**用意できた文しか出さない**——毎回その場で組み立てて見せると、翻訳が済んでいない途中の姿が出て、画面の文と実際に送る文が食い違う。`resolved_prompt_signature`（指示の指紋）と `resolved_prompt_engine` が今と違えば古いと判定し、中身を出さずに作り直しを促す。

音声の出来上がりは文の形に強く左右され、正解は実機でしか分からない。そこで**直接書き直すモード**（`shots.prompt_edit_mode`）を持つ。入にすると、いま使われる文を `edited_prompt_json` へ写して編集できるようにし、その文をそのまま送る（組み立て直さず、翻訳も掛けない）。入の間は文のもとになる指示（動き・セリフ・環境音・音楽・ビート・時間割り）を API 層で拒む——変えても文へ反映されず、画面の指示と実際に送る文が食い違うため。切ると書き直した文は捨て、指示から作った文へ戻る（どちらが使われるのかを曖昧にしない）。

**カット1本だけを取り出す道も残す。**全カットをつなぐ書き出しとは別に、カードから `GET /api/v1/shots/{id}/video` の中身をそのまま保存できる（画面の「保存」）。つなぎ直しも再符号化もしないので ffmpeg を必要とせず、自分の編集ソフトでつなぎたい人と、1カットだけ使いたい人はこちらを使う。

**書き出したmp4はデータ領域（`exports/{project_id}.mp4`）に残る。**作り直すまで有効なので、`GET /api/v1/projects/{id}/export` が実体の有無・日時・大きさを返し、画面を開き直しても「名前を付けて保存」を出せるようにする（「さっき押したかどうか」で消さない）。

**大きさの違うカットは、いちばん大きいカットに合わせて余白で揃える。**書き出しは ffmpeg の concat フィルタで繋ぐが、これは全入力の大きさが同じでないと失敗する（Wan 2.2 の1280x720 と MiniMax H3 の1344x768 を混ぜると実際に失敗した）。そこで各カットの大きさを結合と同じ ffmpeg で先頭のコマから読み（ffprobe は利用者が用意した ffmpeg に付いていないことがあるので頼らない）、画素数の最も多いカットを書き出しの大きさとする。ほかのカットは縦横比を保って拡大・縮小し、縦横比の違う分は黒い余白で埋める（`scale` の `force_original_aspect_ratio=decrease` と `pad`）。切り抜いて埋める方法は絵の端を失うので取らない。小さいほうへ合わせる方法は、大きく作ったカットの細部を捨てるので取らない。大きさが同じカットには何もしないので、揃っている作品の画質は変わらない。

**保存は `<a href download>` に頼らない。**保存するURLがページと別の出どころだと `download` 属性は無視され、押しても何も起きない（デスクトップ版はページが `tauri://`、APIが `http://127.0.0.1:<番号>` で別の出どころになる）。`api.saveFile` が中身を `fetch` で受け取り、`blob:` のURL——これはページと同じ出どころになる——へ直してから保存する。CSPの `connect-src` にAPIを許可してあるので取得はでき、保存はページ自身の出どころで起きる。

**保存先はOSのダイアログで選ばせる。**ブラウザの保存先選択（`showSaveFilePicker`）は使わない——「このサイトにファイルの編集を許可するか」という確認が必ず挟まり、その警告文はこちらから変えられない。ローカルの保存なのに身に覚えのない警告が出て、何を聞かれているのか分からなくなる。

代わりに、デスクトップ版では `tauri-plugin-dialog` を使ったこのアプリのコマンド `choose_save_path` を呼ぶ。このコマンドは**場所を決めるだけで書き込みはしない**。複製は、元のファイルを持っているローカルAPI（`POST .../save-as`）が受け持つ——数百MBの動画を画面の層へ通さずに済むため。プラグインはRustからしか使わないので、JS側の追加依存は要らない（`withGlobalTauri` でこのアプリのコマンドだけを呼ぶ）。

`save-as` は**アプリの保存先の外へ書く唯一の経路**なので、受け取った場所をそのまま信じない。絶対パスであること、親フォルダが実在することをAPI側でも確かめてから複製する。上書きはOSのダイアログがすでに確認しているので妨げない。ブラウザで開いているときはダイアログが無いので、既定の保存先へそのまま落とす。

ファイル名は作品名・シーン名から作る（`safeFileName`）。Windowsが受け付けない文字はここで落とす——残すと保存の段階で弾かれ、何が悪いのか分からないまま止まる。

**保存し終えたことは画面に出す。**保存は成功しても画面が変わらないので、黙って終わると保存できたのか分からない。保存した名前をそのまま添えて知らせる。

Wan 2.2 はこの構造を知らないので、動きの記述だけを素の文として渡す。

人物候補プロンプトでは作品画風、人物固有の雰囲気補正、顔の識別条件を分離する。顔立ちの自由記述は輪郭、眉、目、鼻、口、年齢感を含む最優先条件として配置し、候補ごとの顔デザイン差分は未指定部分だけを補う。作品画風と人物補正は候補・立ち絵の再現情報へ保存する。

状態遷移はリポジトリ層で許可表を検証し、更新は現在状態を条件に含めて競合を検出する。GPUを使うジョブの作成は、実行中判定と登録を不可分に行って二重起動を防ぐ。生成入力は不変JSONスナップショットとして保存し、編集後のプロジェクトデータから独立して再現できるようにする。

## 5. ジョブ状態遷移

```text
queued -> preparing -> running -> validating -> completed
   |          |           |            |
   +----------+-----------+------------+-> failed / cancelled
              +-----------+------------+-> interrupted

interrupted -> queued（再実行）
interrupted -> preparing（対応ジョブのみチェックポイント再開）
```

プロセス起動時、`preparing`、`running`、`validating` は `interrupted` へ原子的に移す。外部ComfyUIのprompt IDがある場合は履歴APIも確認し、既に完了している成果物を回収できる設計へ拡張する。

## 6. ComfyUI互換性層

ワークフローはUI形式ではなくAPI形式JSONを保存する。各テンプレートに必要ノード、モデルスロット、書換可能入力のバインディングを持たせる。接続先の `/object_info` から利用可能ノードを取得し、次の優先順で選択する。

1. 管理環境用の固定コアワークフロー
2. 標準ノードだけの外部環境用ワークフロー
3. 対応カスタムノードを使う最適化ワークフロー
4. 利用不可（不足ノードを日本語で提示）

APIは `/prompt`、`/history/{prompt_id}`、`/view`、`/interrupt` を利用する。ワークフロー書換対象はプロンプト、ネガティブプロンプト、seed、解像度、モデル、LoRA、強度、入力画像、出力接頭辞に限定する。

立ち絵は2511の `TextEncodeQwenImageEditPlus` と参照潜在方式で作り、カメラ角度LoRAの固定トリガー（`<sks> front view eye-level shot wide shot`）を指示文の先頭へ置く。4ステップでは「頭から靴まで入れる」という組み直しが弱いため、Lightningを切り離した20ステップで作る。モデル一覧と必要コアノードは投入前に検査し、不足時は日本語で不足ファイルを提示する。

## 7. モデル管理

モデルマニフェストはモデルID、リビジョン、配布元、ライセンス、相対保存先、サイズ、SHA-256、用途を保持する。スキャンは拡張子、サイズ、更新日時、safetensorsヘッダーを高速取得し、ハッシュは必要時にバックグラウンドジョブで計算する。

ダウンロードは `.part` ファイルへRange要求で再開し、期待サイズとSHA-256を検証してから管理領域内で原子的に確定名へ変更する。外部モデルルートはダウンロード先候補にしない。

## 8. この端末に合わせた既定値

GPUのVRAMと世代、ホストRAMの量で、現実的に使えるモデルと生成方法が変わる。`GET /api/v1/setup/hardware` は構成を調べ、`model-manifests/hardware-profiles.json` と突き合わせて既定値を提案する。しきい値も文言もマニフェスト側にあり、モデル構成を変えたときはJSONだけを直す。

構成は ComfyUI の `/system_stats`（起動中なら空きVRAMまで分かる）を優先し、起動していなければ `nvidia-smi` で調べる。世代（compute capability）は `/system_stats` から取れないため、`nvidia-smi` は接続できる場合も併せて実行して補う。MiniMax H3 のテキストエンコーダーは nvfp4 版のため Blackwell（12.0）以降が要り、VRAMの量だけでは判断できないためである。どちらからも読めないときは `detected=false` を返し、**何も勧めない**（当てずっぽうの既定を書き込むと、動かない組み合わせを既定にしてしまう）。

提案は段（tier）で大枠を決め、選択肢ごとの条件（VRAM・RAM・世代）を満たさないときは `fallback` をたどって下げ、下げた理由を添えて返す。提案するだけでは何も変わらず、利用者が「おすすめ設定を使う」を押したときだけ `preferences` へ書き込む。

`preferences` は「前回選んだ生成方法・枚数」を鍵と値で持つ（合成の丁寧さ、動画の作り方、候補の枚数、変化強度、立ち絵の枚数）。書き出しのfpsはここに持たず、カット動画が実際に持つfps（mp4は結合に使うffmpeg本体の入力情報、Wanのwebpはコマの表示時間。ffprobeは利用者が用意したffmpegに付いていないことがあるので頼らない）を書き出しのたびに読んで合わせる。作品ではなく**この端末の使い方**なので作品には紐づけない。項目を増やしても列の追加が要らず、知らない鍵は読み飛ばす。値は文字列で持ち、読むときに項目ごとの型で検証して、壊れた値はその項目だけ既定へ戻す。画面で選び直した値はそのまま次回の既定になり、おすすめが後からそれを上書きすることはない。

## 9. セキュリティと障害分離

- APIは `127.0.0.1` に限定し、CORSは開発時の明示Originだけ許可する。
- 任意URL接続ではHTTP/HTTPS、ホスト、ポートを検証し、初期版はループバック接続を既定とする。
- 任意ワークフローやシェル文字列を利用者入力から組み立てない。
- パスは正規化し、シンボリックリンク／ジャンクション解決後の管理領域境界を確認する。
- API と ComfyUI を別プロセスにして、CUDA OOMや依存破損をUIから隔離する。

## 10. 人物・背景・静止画の生成

### 10.1 人物の実体は立ち絵

人物ごとの学習（LoRA）は行わず、全身・正面・素背景の**立ち絵**を人物の実体にする。Qwen-Image-Edit-2511 は全身の立ち絵1枚を渡せば、同一性を保ったまま姿勢・向き・場面を変えられる。比較実験では、胸から上の画像より正面全身の方が良く、三面図や向き違いの画像を個別に渡す方法とほぼ互角だった。正面全身が1枚あれば、合成のときに姿勢を指定しても許容範囲に収まるため、立ち絵は1行＝1枚とする。学習の準備・待ち時間・採否の判断に見合う差は出ない。

衣装・小物は立ち絵が持つ。合成で変えるのではなく、**立ち絵の変更**で別の1枚へ焼き込む。そのため挿絵の合成には小物を渡さない。合成へ渡せる画像は3枚までで、人物2人と背景で埋まるためでもある。

使うモデルは、アプリの利用や出力画像に新たな制限を加えるライセンスのものを避ける。

### 10.2 生成の経路

| 工程 | モデル | ワークフロー | 入力 |
|---|---|---|---|
| 人物候補 | Z-Image-Turbo | `z_image/zimage_candidate_core.json` | 文だけ |
| 背景・小物 | Z-Image-Turbo | `z_image/zimage_basic_core.json` | 文だけ |
| 立ち絵（基準画像から） | Qwen-Image-Edit-2511＋角度LoRA | `z_image/qwen_character_reference_2511_angles_external.json` | 基準画像1枚 |
| 立ち絵の変更 | Qwen-Image-Edit-2511 | `composition/qwen_scene_composition.json` | 立ち絵1＋小物0〜2 |
| 背景のバリエーション（小物を置く） | Qwen-Image-Edit-2511 | 同上 | 元背景1＋小物1〜2 |
| 背景のバリエーション（時間帯・天気） | Qwen-Image-Edit-2511 | 同上 | 元背景1枚だけ |
| 静止画の合成 | Qwen-Image-Edit-2511 | 同上 | 立ち絵1〜2＋背景1 |

立ち絵の変更・背景のバリエーション（まとめて「派生」）と合成は同じテンプレートを使い、**指示文の組み立てだけを分ける**（`derivation.py` と `composition.py`）。テンプレートを写して分岐させると、同じ指定から違う文が出る。

立ち絵の初回生成に角度LoRAを使うのは、正面全身へ構図を作り直すのに `<sks> front view eye-level shot wide shot` の語順が要るため（`ANGLE_CONTROL_PROMPTS["full_front"]`）。派生は向きを変えないので角度LoRAは要らない。派生は**高速化LoRA無しの丁寧な設定で作る**。4ステップでは「衣装を変える」「置く」「時間帯を変える」という指示も、全身・素背景という立ち絵の条件も守られない。

### 10.3 静止画の合成の指示文

保つものと変えるものを分けて言う。

- 保つ: 顔、髪型、髪の色、目の色、体型、衣装・小物、画風
- 変える: 姿勢、しぐさ、体の向き、表情

姿勢の指定が空なら「元の姿勢のまま」を出す。空欄に文を当てず、引数で外から切り替えることもせず、指定の有無で決める。

姿勢・表情・配置は、人物ごとに `the first person in image 1` のように画像の番号へ結び付けて書く。番号を宣言してから状況を別の文に置くと、人物が複数いるとき誰の話か決まらない。人数は言い切る（`_people_count`）。素材の名前は渡さない（画面の中へ文字として描かれる）。

人物ごとの指定は**日本語のまま渡す**。配置を英語にすると人物が増えた実測があるので、まとめて英語化しない。日本語の配置（「右寄り」など）は立ち絵を渡す経路なら効く。

**時間帯は合成の状況説明では変えられない**（夕日の教室に「真昼」と書いても夕日が残る）。時間帯を変えたいときは、背景のバリエーションとして別の1枚を作る。

### 10.4 派生の指示文

**立ち絵の変更**は、出来上がりが立ち絵の条件を満たすことを指示文で担保する。崩れると、次の合成で使えない画像が立ち絵の一覧に混ざる。

- 全身（頭のてっぺんから靴まで、足が枠の中）。腰や腿で切らない
- 素背景（薄いグレー、風景を描かない）
- 人物は1人だけ、1回だけ
- 顔・髪・目の色・体型・画風・姿勢は元の立ち絵のまま。変えるのは衣装・持ち物だけ

衣装は画像が無くても文だけで指定できる。

**背景のバリエーション**は、場所・構図・カメラ位置・遠近を元の背景のまま保ち、毎回「人物を描かない」と言い切る（状況を書く文が入ると人物が湧く）。同じモデルでも、入力が背景1枚だけの編集なら時間帯を変えられ、人物や小物と一緒に渡すと変えられない。このため「小物を置く」と「時間帯・天気を変える」は作り方を分け、時間帯の回は小物を受け取らない（受け口で断る）。

小物を置く回は「image 1 の編集」だと言い切る。「小物を image 1 の場所へ置け」とだけ書くと、小物を主役に据えた別の場面が描かれ、元の背景が残らない。元の背景が残るのは、次の3つを言ったとき。

- image 1 を編集し、そこへ小物を足す
- 小物の画像は見た目の参考だけで、その構図・カメラ・周りは使わない
- image 1 に元からあるものは動かさない・消さない・描き直さない

小物を複製して2つ描くことがあるため「1回だけ描く」も足す。

`background_assets.base_asset_id` は常にグループの元を指す。親をたどる形にすると、一覧を出すたびに木をたどることになり、途中を消したときに群れが割れる。元背景を消してもバリエーションは残る（`ON DELETE SET NULL` で、それぞれが元になる）。

### 10.5 既知の課題

- **小物を2つ渡す（画像3枚）と、種を3つ変えて試すと1つはカメラが寄って構図が変わる。** 参照画像の縦横比を変える `FluxKontextImageScale` を外すと悪化したので、縮尺は原因ではない。
- **合成の指示文の組み立て方は、まだ比べ切っていない。** 人物ごとの指定を1文にまとめるか分けるか、姿勢・表情を日本語のまま渡すか英語へ直すか、状況説明と人物ごとの指定が食い違うときにどちらを先に置くか。比べるときは同じ種・同じ立ち絵で、1度に1つだけ変える。

- [ComfyUI Qwen-Image-Edit公式例](https://docs.comfy.org/tutorials/image/qwen/qwen-image-edit)：画像入力、Qwen-VL、VAE、編集モデルを使う人物保持編集経路。
- [ComfyUI Qwen-Image-Edit-2511公式例](https://docs.comfy.org/tutorials/image/qwen/qwen-image-edit-2511)：2511用エンコード、参照潜在方式、4-step Lightningの構成。
- [Qwen-Image-Edit-2511 Multiple Angles LoRA](https://huggingface.co/justabigduck/Qwen-Image-Edit-2511-Multiple-Angles-LoRA)：96角度の固定トリガー、推奨強度、Apache-2.0ライセンス。
