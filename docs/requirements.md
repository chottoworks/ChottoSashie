# 要件定義書

## 1. 目的と対象

ちょっと挿絵は、物語の同一人物を保った挿絵と、その挿絵から作る短い動画をローカルPCで作成するWindowsデスクトップアプリである。初期版はWindows 11 64bit、NVIDIA CUDA対応GPU、単一ユーザー、日本語UIを正式対象とする。

想定利用者は、**すでにComfyUIで画像を作っている人**である。ComfyUI・LoRA・プロンプトといった言葉は通じる前提に立ち、画面でも言い換えない。ただし、人物を一貫した手順で作り切るところ（人物候補→基準画像→立ち絵）はこのアプリが受け持ち、ノードグラフを組ませない。

生成エンジンにはComfyUI APIを用いるが、通常画面にはノードグラフを露出しない。Z-Image-Turboを人物候補と背景・小物の生成に、Qwen-Image-Edit-2511を立ち絵の生成と静止画の合成に、Wan 2.2／MiniMax H3をカットの動画生成に利用する。人物ごとの学習（LoRA）は行わない。

## 1.1 動作要件

| | 最低 | 推奨 |
|---|---|---|
| GPU | NVIDIA製・VRAM 12GB以上 | VRAM 16GB以上 |
| メモリ | 32GB | 48GB以上 |
| 保存先の空き | 80GB以上（挿絵のみ） | 120GB以上（動画も作る場合） |
| ディスク | SSD | NVMe SSD |
| OS | Windows 11 64bit | — |

数値の根拠は、静止画の合成に使う Qwen-Image-Edit-2511（fp8mixed・約20.5GB）とそのテキストエンコーダー（約9.4GB）である。これがVRAMへどれだけ載るかで、1枚あたりの待ち時間が桁違いに変わる。VRAM 12GB未満では生成のたびにモデルの出し入れが起き、1枚に数分以上かかって実用にならない。

音声付きの動画（MiniMax H3）だけは、VRAM 24GB以上かつBlackwell世代（RTX 50xx以降）を要する。これは任意機能で、満たさない場合はWan 2.2（映像のみ）を使う。

**要件を満たさない端末でも起動と操作はできる。** ただしその旨を初期設定で伝え、数十GBのモデルを取得する前に、承知したうえで進むことを確かめる。判定の値は[`model-manifests/hardware-profiles.json`](../model-manifests/hardware-profiles.json)の `requirements` に置き、画面・文書・判定が同じ値を見る。

## 2. 利用者に見せる概念

利用者向けの主要概念を、作品、登場人物、背景、小物、人物候補、基準画像、立ち絵、静止画、シーン、カットに限定する。人物の実体は「立ち絵」と呼んで通す（画面ごとに別名で呼ばないため）。一方、seedの扱いや指示文の組み立てのように、決めても結果を予測できないつまみは表に出さない。呼び方と、画面に出す言葉の線引きは[用語辞書](terminology.md)に合わせる。

## 3. MVP機能要件

### 3.1 初回セットアップ

まず「挿絵だけ作る」か「挿絵と動画を作る」かを選ぶ。動画を作らない場合、シーン・カット・書き出しの画面は出さず、動画用モデルも取得しない。あとから変えられる。

接続方法として「全部自動で準備」「既存モデルを利用」「既存ComfyUIをそのまま利用」を提供する。管理環境はバージョン固定し、モデル等は初回起動後に段階的に取得する。

既存モデル利用では、外部モデルフォルダを読み取り専用参照として登録し、不足分だけをアプリ専用領域へ保存する。既存ComfyUI利用では、指定フォルダまたはURLからAPI互換性を検査し、不足機能のみ無効化する。

### 3.2 必要環境の確認（画面では「ノードとモデルの確認」）

接続先ComfyUIの `/object_info` を読み、機能ごとに必要なノードとモデルが揃っているかを確認する。確認の単位は「背景・小物の生成」「静止画の合成」「立ち絵の作成」「カットの動画生成」で、動画を作らない設定では動画の項目を対象から外す。

不足があれば、その場で対処できる操作（ComfyUI本体の準備・入れ替え、不足モデルの取得、専用ComfyUIの起動）を不足の説明のそばに出す。生のエラーだけを見せず、何をすれば解消するかを日本語で示す。

確認はComfyUIに聞いて行うため、聞ける状態になったら自動で始める（既存ComfyUIは設定を保存した時点、専用ComfyUIは起動して応答した時点、モデルを取り終えた時点）。画面では独立した段にせず、「ComfyUI環境を用意」の最後の手順として置く。手で確かめ直すボタンは、一度確かめたあとに、何をしたあとに押すものかを添えて出す。

### 3.3 登場人物と立ち絵

プロフィールは名前、性別・年齢帯、顔、髪、目、体格、衣装、装飾品、性格、固定特徴、画風、自由記述を保持する。色や固定特徴は構造化して保存する。

Z-Image-Turboによる8〜12候補から基準画像を一枚選び、外見特徴をロックする。基準画像からQwen-Image-Edit-2511＋角度LoRAで**立ち絵**（全身・正面・素背景の1枚）を作る。立ち絵がその人物の実体で、静止画の合成はこれを使う。手持ちの全身画像をそのまま立ち絵として登録してもよい。

立ち絵は人物ごとに何枚でも持てる。静止画ごとにどれを使うか選び、選んでいないときに使う1枚を既定の立ち絵とする。立ち絵の並びは利用者が左右へ入れ替えられる。新しい立ち絵は末尾（右端）、複製は元のすぐ右に入る。既定を選んでいないうちは、並びの先頭の1枚が既定になる。

立ち絵は1回に1枚作る。**立ち絵の変更**では、いまある立ち絵と小物（2つまで）または文だけの指示から、衣装・持ち物を変えた1枚を作る。顔・髪・体格・画風は元の立ち絵のまま、姿勢も変えない。出来上がりは採用するまで反映せず、見比べて「採用する」（元の立ち絵を置き換える）か「再生成する」（同じ指示で作り直す）かを選ぶ。元の立ち絵も残したいときは、先に「複製」で同じ立ち絵を1枚増やし、複製した方を変更する。これにより、人物二人と背景の合成に小物を含められる（小物そのものを合成へ渡さずに済む）。

### 3.4 人物ごとの学習は行わない

人物ごとのLoRA学習は対象外とする。Qwen-Image-Edit-2511は全身の立ち絵1枚で同一性を保てるため、学習の準備・待ち時間・採否の判断に見合う差が出ない（比較実験による判断。理由は[アーキテクチャ](architecture.md)の10.1）。

### 3.4.5 背景のバリエーション

元の背景から、小物を置いた背景や、時間帯・天気を変えた背景を作れる。場所・構図・カメラ位置・遠近は元のまま保ち、人物は描かない。同じ元から派生したものはグループとして一覧に並べ、元を消しても派生は残す。

時間帯・天気を変えるときは、元の背景1枚だけを渡す。人物や小物を一緒に渡す合成では時間帯を変えられないため、作り方として分ける。

### 3.5 静止画

背景1枚と、登場人物（最大2人）の立ち絵を選び、状況の説明文を添えて1枚へ合成する。挿絵として使う場合はここが完成地点になる。

姿勢・表情・向き・立ち位置は、人物ごとの指定として合成のときに渡す。書かなければ立ち絵のままの姿勢になる。衣装は立ち絵が持つので合成では変えない（変えたいときは別の立ち絵を作る）。小物は合成へ渡さない。再現に必要なモデルID、バージョン、ワークフロー、入力、seedを保存する。

### 3.6 シーンとカット（動画を作る場合のみ）

静止画1枚が1つのシーンになる。シーンに動きの指示を持つカットを足し、静止画を起点にImage-to-Videoで動かす。前カットの最終フレームを次カットの起点へ引き継いで連続性を保ち、全カットを物語順に1本の動画へ書き出す。

初回セットアップで「挿絵だけ作る」を選んだ場合、この節の画面は出さず、動画用モデルも取得しない。

### 3.7 ジョブと復旧

ジョブ状態は `queued`、`preparing`、`running`、`validating`、`completed`、`failed`、`cancelled`、`interrupted` とする。状態と進捗をSQLiteへ永続化し、アプリ起動時に残存する `preparing`、`running`、`validating` を `interrupted` へ移す。利用者は安全な再実行または対応機能での再開を選べる。

## 4. 非機能要件

- 外部ComfyUI、カスタムノード、モデル、設定をアプリが更新・削除・移動・改名・上書きしない。
- 外部パスは既定で読み取り専用とし、書き込み可能性の検査も実際の試験ファイルを作らずACL／属性を参照して行う。
- モデル取得は一時ファイル、再開、容量表示、完了検証、SHA-256、固定バージョン、ライセンス表示に対応する。
- アプリ本体・ランタイムと大容量データを分離し、Cドライブ以外、日本語、空白、長いパス、取り外しドライブを扱う。
- APIはループバックのみで待ち受け、起動ごとの認証トークンをTauriから渡す。
- ログにプロフィール、プロンプト、ローカルパスを無制限に出力しない。
- SQLiteはWALモード、外部キー制約、短いトランザクションを用いる。

## 5. MVP外

AMD／Intel GPU、macOS、Linux、三人以上、高度なポーズ編集、人物ごとの学習、クラウド／複数PC同期、一般利用者のワークフロー編集、自動アップデートはMVP外とする。二人の領域別処理は次段階とする。

## 6. 受け入れ基準（基盤フェーズ）

- WindowsでAPIとReact画面が起動し、ヘルスチェックと診断結果を表示できる。
- SQLite DBを初期化し、許可された状態遷移だけでジョブを更新できる。
- 再起動時に実行中状態を中断状態へ復旧できる。
- 指定したComfyUI／モデルルートを変更せず検査できる。
- ComfyUIの `/object_info` を検査し、対応ワークフロー選択または不足ノードを返せる。
- テスト用ワークフローを `/prompt` へ投入し、ComfyUIのprompt IDをジョブへ保存できる。
